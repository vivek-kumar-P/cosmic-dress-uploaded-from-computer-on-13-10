## 2. Schema Changes Made

### Dropped from `profiles` table
- `address` (text, nullable) — removed. Data was safely migrated to `street_address` via the migration's `UPDATE` statement before column drop.

### Kept in `profiles` table (unchanged)
- `street_address` — now the canonical single-line street address field
- All other profile fields preserved unchanged

### New table: `user_addresses`
A normalized table to support multiple shipping addresses per user:
- `id` uuid PK
- `user_id` uuid FK → `auth.users(id)` ON DELETE CASCADE
- `full_name`, `phone` — per-address contact info
- `address_line_1` (NOT NULL), `address_line_2`
- `city` (NOT NULL), `state`, `country` (NOT NULL), `postal_code`
- `is_default` boolean — enforced as single-default by trigger
- `created_at`, `updated_at` timestamps

### New table: `user_preferences`
A normalized table to store explicit fashion preferences for personalization:
- `id` uuid PK
- `user_id` uuid FK → `auth.users(id)` ON DELETE CASCADE UNIQUE (one record per user)
- `preferred_styles`, `preferred_colors`, `preferred_sizes`, `preferred_categories`, `preferred_occasions` — all `text[]` arrays
- `created_at`, `updated_at` timestamps

## 3. Migration File Created

**File:** [`scripts/26-create-onboarding-database-foundation.sql`](file:///E:/cosmic-dressing-using-antigravity/scripts/26-create-onboarding-database-foundation.sql)

**What it does:**
1. Creates `public.user_addresses` with RLS enabled and 4 policies
2. Creates `public.user_preferences` with RLS enabled and 4 policies
3. Creates indexes on FK columns (`user_id`) and `is_default`
4. Creates `ensure_single_default_address()` trigger function and trigger
5. Attaches `update_updated_at_column()` triggers to both new tables
6. Safely migrates `profiles.address` data → `profiles.street_address`
7. Drops `profiles.address` column

All changes are wrapped in `BEGIN`/`COMMIT` for atomic execution. Uses `IF NOT EXISTS` and `IF EXISTS` guards for idempotency.

## 4. Address Migration Decision

### Summary

| Field | Status | Decision |
|-------|--------|----------|
| `profiles.address` | **Dropped** | Consolidated into `street_address` |
| `profiles.street_address` | **Kept** | Canonical single-line street address field |
| `user_addresses` table | **Created** | Normalized multi-address table for future checkout |

### Migration Safety
The migration first copies `address` → `street_address` where `street_address IS NULL OR street_address = ''`:
```sql
UPDATE public.profiles
SET street_address = COALESCE(street_address, address)
WHERE street_address IS NULL OR street_address = '';
```
Only then does it drop the `address` column. No data is silently discarded.

### Current State (Before Migration Applied)
- `profiles.street_address` — used by Settings tab, checkout pre-fill, profile display
- `profiles.address` — used by Onboarding flow (now remapped in code to write `street_address`)
- Both columns currently exist in the live database

### After Migration Applied
- `profiles.address` — dropped
- `profiles.street_address` — single canonical source for inline street address
- `user_addresses` — available for future multi-address onboarding/checkout integration

## 9. Data Migration Performed

**NOT APPLIED YET** — data migration is contained inside `scripts/26-create-onboarding-database-foundation.sql`.

The migration's data safety steps:
```sql
-- Step 1: Copy address → street_address where street_address is blank
UPDATE public.profiles
SET street_address = COALESCE(street_address, address)
WHERE street_address IS NULL OR street_address = '';

-- Step 2: Only then drop address column
ALTER TABLE public.profiles DROP COLUMN IF EXISTS address;
```

This ensures:
- No data is lost for users who filled in onboarding (`address` was the onboarding field)
- Users who filled in Settings (`street_address`) are unaffected
- The `COALESCE` only fills in `street_address` when it was blank — it does not overwrite existing data

## 17. Outstanding Item — Stale types/supabase.ts

The `types/supabase.ts` file was regenerated by the user, but the output does not reflect the live schema. The `profiles` table in the generated types only shows 8 basic columns (id, email, username, full_name, avatar_url, bio, created_at, updated_at) and is missing all Phase 1 extended columns (`phone`, `website`, `street_address`, `city`, `state`, `postal_code`, `country`, `onboarding_completed`). The `user_addresses` and `user_preferences` tables are absent.

**Root cause:** The Supabase CLI generates types based on the remote database's PostgREST API schema. If the migration was applied, the most likely cause is that the CLI was run against a cached schema, a different schema was selected, or the CLI is not authenticated to the correct project.

**Impact on the application:** LOW. The application does **not** use `Database["public"]["Tables"]["profiles"]["Row"]` as its `Profile` type. The authoritative `Profile` interface lives in `contexts/auth-context.tsx` (line 8–25) and is manually maintained — it correctly includes all extended columns including `street_address`.

**What is not blocked:** Phase 3 onboarding UI implementation does not depend on `types/supabase.ts` being complete. All Supabase client calls in this project pass through `auth-context.tsx` helpers or use `as any` casts where needed.

**Recommended resolution (for the user, before Phase 3 is complete):**

```bash

npx supabase projects list

# Re-run with explicit schema and verbose output
npx supabase gen types typescript --project-id eldilupnubviqrhndyvk --schema public > types/supabase.ts

# Then verify the output contains user_addresses:
```

If the generated types still do not include the new tables, verify the migration was actually applied by running the verification queries from Section 3 of this report in the Supabase SQL Editor.
